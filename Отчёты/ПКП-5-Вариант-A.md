# Отчёт по практической работе 5. Вариант A

Проект находится в `ПКП-5/Вариант-A`. В варианте A через Kafka передаётся команда создания заявки `Application`. Пример с `Order` оставлен отдельно как общий walkthrough и не является реализацией варианта A.

## Что сделано

Для варианта A выбрана операция создания заявки. В топик записывается команда `application.create`, а не событие о готовой заявке. Payload содержит автора и тему. Доменные проверки выполняет worker, поэтому запись в Kafka ещё не означает, что заявка создана.

Конверт содержит `command_id`, тип и версию команды, `aggregate_id`, время запроса, `correlation_id` и `payload`. Ключом записи служит идентификатор заявки. Благодаря этому все действия с одной заявкой оказываются в одной партиции и сохраняют порядок. Топик `application.commands.v1` создаётся с тремя партициями.

Добавлены две программы:

- `cmd/application-command-producer` формирует envelope и отправляет его с `acks=all`;
- `cmd/application-command-worker` состоит в группе `application-command-v1`, создаёт заявку и фиксирует offset вручную.

Автоматическая фиксация offset отключена. `CommitRecords` вызывается только после успешного `ProcessApplication`. В consumer включён `BlockRebalanceOnPoll`, а `AllowRebalance` вызывается после обработки набора записей. При ошибке offset не фиксируется. Повторная доставка определяется по `command_id`.

В `compose.yaml` закреплён образ `apache/kafka:4.3.1`. Kafka запускается без ZooKeeper, с ролями broker и controller. Отдельный `kafka-init` идемпотентно создаёт нужный топик. В `go.mod` закреплён `github.com/twmb/franz-go v1.21.5`.

## Контракт 202 Accepted

Для HTTP ingress принят следующий смысл ответа:

```http
HTTP/1.1 202 Accepted
Location: /v1/operations/cmd-app-1

{"operation_id":"cmd-app-1","status":"ACCEPTED"}
```

Такой ответ разрешён только после подтверждённой публикации в Kafka. `ACCEPTED` означает, что транспорт принял команду, но не то, что заявка прошла бизнес-проверки. Ресурс операции затем должен показывать `PROCESSING`, `SUCCEEDED` или `REJECTED`.

Клиент передаёт `Idempotency-Key`. Повтор с тем же ключом и тем же телом возвращает исходный `operation_id` без второй публикации. Если тело отличается, корректным ответом будет `409 Conflict`. При тайм-ауте или ошибке Kafka ответ `202` возвращать нельзя.

## Фактическая проверка Kafka

Docker в системе был доступен. Kafka 4.3.1 запустилась, команда `kafka-metadata-quorum.sh` подтвердила KRaft-кворум с controller `1`. Описание топика показало три партиции и replication factor 1.

Я запустил два экземпляра worker. После rebalance первый обслуживал партиции 0 и 1, второй — партицию 2. После остановки второго экземпляра партиции были переданы оставшемуся участнику группы.

В топик отправлено 30 команд. По партициям они распределились как 8, 9 и 13 сообщений. После обработки для каждой партиции `CURRENT-OFFSET` совпал с `LOG-END-OFFSET`, lag был равен нулю.

Время разбора backlog в миллисекундах я не записывал как результат, потому что сообщения отправлялись через отдельные `go run` контейнеры. Они каждый раз загружали модули, и итоговое время отражало бы в основном подготовку Go, а не скорость consumer. В `docs/experiments/02-kafka.md` оставлен runbook для чистого замера с заранее собранными программами.

## Тесты

Для `Application` добавлены тесты успешного декодирования и передачи payload, отклонения команды неправильного типа и пустого обязательного поля. Существующие тесты заказа и предыдущих работ сохранены.

Локального Go в `PATH` не было, поэтому команды выполнены в официальном контейнере `golang:1.26.8`. Результаты:

```text
gofmt -w .          — успешно
go vet ./...        — успешно
go test ./...       — успешно
go test -race ./... — успешно
docker compose config — успешно
```

Ошибок тестов и сообщений race detector не было.
