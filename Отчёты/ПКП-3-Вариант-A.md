# Отчёт по практической работе 3 (ПКП-3). Вариант A «Заявка на согласование»

Проект: `ПКП-3/Вариант-A/` (модуль `example.com/orderflow`)

Окружение: Windows 10 Pro 22H2 (`10.0.19045`), Go `1.26.8 windows/amd64`, CPU Intel Core i9-10850K. Для race detector использованы `CGO_ENABLED=1` и MinGW-w64 GCC.

## 1. Цель работы

Продолжить проект ПКП-2 и реализовать конкурентную обработку заявок с фиксированным числом workers и конечной очередью. Также требовалось обработать переполнение очереди, корректно завершать goroutine и измерить contention.

## 2. Реализация

Создан пакет `internal/platform/workqueue`. Очередь запускает worker goroutine, передаёт им задания через ограниченный канал и учитывает завершение через `sync.WaitGroup`. Метод `Submit` не блокирует HTTP handler: при заполнении очереди он возвращает `ErrFull`. Метод `Close` запрещает новые задания, закрывает входной канал и ждёт обработки уже принятых заданий. Если время остановки истекло, контекст workers отменяется.

Конфигурация дополнена переменными:

- `WORKERS`, значение по умолчанию `4`, допустимы только целые значения от `1` до `64` включительно;
- `QUEUE_CAPACITY`, значение по умолчанию `32`, допустимо неотрицательное целое.

HTTP API дополнен маршрутом `POST /applications/{id}/submit`. Принятая в очередь команда получает `202 Accepted`. При заполнении очереди возвращается `429 Too Many Requests` и заголовок `Retry-After: 1`. После закрытия очереди возвращается `503 Service Unavailable`. Бизнес-операция `application.Service.Submit` выполняется worker, а её ошибка поступает в структурированный журнал через обработчик ошибок очереди.

При остановке процесс сначала снимает readiness и прекращает приём HTTP-запросов. Затем он закрывает очередь в пределах общего `SHUTDOWN_TIMEOUT`. Для каждой goroutine определены владелец, источник заданий и способ остановки.

## 3. Детерминированные тесты

Синхронизация тестов очереди выполнена каналами, без `time.Sleep`:

- занятый worker и заполненный буфер воспроизводят `ErrFull`;
- `Close` дренирует все принятые работы и запрещает новые;
- отменённый shutdown context отменяет выполняемую работу;
- HTTP-тесты проверяют `202` и фактический переход заявки в `SUBMITTED`;
- заполненная очередь детерминированно проверяет `429` и `Retry-After: 1`;
- конфигурационные тесты проверяют корректные и недопустимые значения `WORKERS` и `QUEUE_CAPACITY`.

## 4. Benchmark и профиль

Benchmark `BenchmarkQueueContention` измерен с 1, 2, 4 и 8 workers по три запуска. Получены диапазоны: 1 worker `1853-2143 ns/op`, 2 workers `1082-1389 ns/op`, 4 workers `598,3-1023 ns/op`, 8 workers `504,5-536,6 ns/op`. Во всех сериях: `24 B/op`, `1 allocs/op`.

CPU-профиль для 8 workers доступен. Контрольный запуск дал `534,6 ns/op`; наиболее крупные flat-значения: тело работы `44,30%`, `runtime.semasleep` `23,72%`, `runtime.procyieldAsm` `7,26%`, `runtime.semawakeup` `6,55%`. Полный фактический протокол находится в `docs/experiments/02-contention.md`.

## 5. Проверка

Выполнены команды:

```text
go fmt ./...
go vet ./...
go test ./...
go test -race ./...
go test ./internal/platform/workqueue -run '^$' -bench BenchmarkQueueContention -benchmem -count=3
```

Все проверки завершились успешно. Race detector не обнаружил гонок данных.

## 6. Вывод

Пул ограничивает число одновременно выполняемых заданий, а конечная очередь не даёт бесконтрольно накапливать работу. При переполнении API возвращает `429` и `Retry-After`. Значение `WORKERS` проверяется в диапазоне `1..64`. В benchmark данный CPU-bound сценарий ускорялся до 8 workers; CPU-профиль также показал расходы на синхронизацию.
