## 1. Введение

Работа выполняется по разделу 1 практики: программа, отвечающая на `curl`,
ещё не является надёжным сервисом. Как только процесс попадает в среду
управления контейнерами, от него требуются обработка уведомлений об
остановке, честные проверки состояния, структурированный журнал и
ограниченное ожидание активных запросов. Все эти требования относятся
не к бизнес-логике, а к жизненному циклу процесса, и проектируются до
подключения внешних систем.

Создаётся первый процесс учебной системы OrderFlow — `order-command`.
Он не создаёт задачу: каркас задаёт явную конфигурацию, единую точку
сборки зависимостей (`run`/`main`), проверки живости и готовности,
`log/slog`-журнал и мягкую остановку с бюджетом. Поверх каркаса реализованы
пять требований варианта B.

## 2. Задача

Обязательная часть (раздел 3 практики): каркас с `Config`
(HTTPAddr/ShutdownTimeout/LogLevel), обработчик с `/livez`, `/readyz`,
`/slow`, `atomic.Bool`, `requestLog`, `writeJSON`; `main` с разделением
`run()`, `signal.NotifyContext`, каналом `serverErr` с буфером 1,
`SetReady(false)` → `Shutdown` от `context.Background()` с бюджетом,
`ReadHeaderTimeout`/`IdleTimeout`.

Вариант B (раздел 4, все 5 пунктов):

1. `MAX_BODY_BYTES` — положительное целое число байт, по умолчанию 1 MiB,
   с различением трёх классов ошибок разбора.
2. `POST /jobs` — обязательное реальное чтение тела через
   `http.MaxBytesReader` + `io.ReadAll` с проверкой ошибки; успех → 202,
   превышение → 413.
3. Идентификатор запроса `X-Request-ID` с явным контрактом валидации,
   генерацией через `crypto/rand`, возвратом в заголовке ответа и
   помещением в контекст; журнал события приёма задачи с полями
   `request_id`, `body_bytes` (фактически прочитанные байты, не
   Content-Length), `duration_ms`.
4. Тесты превышения размера (413) и отказа при отрицательной готовности
   (503) с проверкой допуска ДО чтения тела и зафиксированной точкой
   принятия операции.
5. Опыт остановки во время медленной загрузки тела: интеграционный тест
   на настоящем слушателе + реальный запуск с curl `--limit-rate`.

Смысл кодов ответов — это разные причины и разные ветви обработчика:
- **202 Accepted** — запрос принят к обработке, а не завершён. Очередь в
  учебной версии не реализована, поэтому 202 здесь лишь демонстрирует
  форму будущего асинхронного интерфейса: долговременное хранение и
  выполнение задачи НЕ гарантируются (оговорка зафиксирована и в коде,
  и в настоящем отчёте);
- **413 Content Too Large** — отказ из-за превышения `MAX_BODY_BYTES`
  (ветвь ошибки `io.ReadAll`, распознаваемая через `*http.MaxBytesError`);
- **503 Service Unavailable** — временная невозможность принять работу
  (ветвь проверки допуска до чтения тела).

## 4. Реализация по шагам

### 4.1. Пункт 1 — MAX_BODY_BYTES с тремя классами ошибок

Значение по умолчанию выбрано явно: `DefaultMaxBodyBytes = 1 << 20`
(1 MiB = 1048576 байт). Разбор выполняет `strconv.ParseInt(raw, 10, 64)`;
ветви различаются по состоянию ошибки (раздел 3.1 практики о разнице
входов `tomorrow`/`0s` применима и здесь: синтаксический отказ и
семантический — разные проверки):

```go
value, err := strconv.ParseInt(raw, 10, 64)
if err != nil {
    var numErr *strconv.NumError
    if errors.As(err, &numErr) && errors.Is(numErr.Err, strconv.ErrRange) {
        return 0, fmt.Errorf("parse MAX_BODY_BYTES: value %q is out of range for int64", raw)
    }
    return 0, fmt.Errorf("parse MAX_BODY_BYTES: value %q is not a number", raw)
}
if value <= 0 {
    return 0, fmt.Errorf("MAX_BODY_BYTES must be positive, got %d", value)
}
```

Три класса — три разные ветви с отдельными сообщениями: (а) «is not a
number», (б) «must be positive», (в) «out of range for int64». Тесты
покрывают все три (`TestMaxBodyBytesSyntaxError`, `TestMaxBodyBytesNonPositive`,
`TestMaxBodyBytesOutOfRange`), успешный разбор (`TestLoadParsesMaxBodyBytes`)
и значение по умолчанию (`TestLoadDefaults`, ровно 1048576).

Фактический вывод реального запуска `order-command.exe` с некорректными
значениями (код выхода 1 в каждом случае):

```
MAX_BODY_BYTES=abc exit=1 => load config: parse MAX_BODY_BYTES: value "abc" is not a number
MAX_BODY_BYTES=-5 exit=1 => load config: MAX_BODY_BYTES must be positive, got -5
MAX_BODY_BYTES=99999999999999999999 exit=1 => load config: parse MAX_BODY_BYTES: value "99999999999999999999" is out of range for int64
```

### 4.2. Пункт 2 — POST /jobs с обязательным чтением тела

Обработчик обязан прочитать данные и проверить ошибку — одного создания
`http.MaxBytesReader` недостаточно (раздел 2.6: функция ограничивает объём
чтения). Ключевой код:

```go
if !h.ready.Load() {
    writeJSON(w, http.StatusServiceUnavailable, map[string]string{"status": "not_ready"})
    return
}
...
body, err := io.ReadAll(http.MaxBytesReader(w, r.Body, h.maxBodyBytes))
if err != nil {
    var maxErr *http.MaxBytesError
    if errors.As(err, &maxErr) || err.Error() == "http: request body too large" {
        ...
        writeJSON(w, http.StatusRequestEntityTooLarge, map[string]any{
            "error": "request body exceeds MAX_BODY_BYTES", "limit_bytes": limit,
        })
        return
    }
    ...
}
```

Превышение распознаётся типизированной ошибкой `*http.MaxBytesError`
через `errors.As`; сравнение со строкой `"http: request body too large"`
оставлено как резервный путь для старых версий Go. Успешное чтение →
`202 Accepted` c `{"status":"accepted"}`. Честная оговорка (в комментарии
кода и здесь): очередь не реализована, 202 означает принятие к обработке,
а не завершение задачи, — долговременное хранение не гарантируется.

### 4.3. Пункт 3 — идентификатор запроса и поля журнала

Контракт валидации задан явно: длина 8–64, символы A–Z, a–z, 0–9, дефис,
подчёркивание (`validRequestID`, проверка по байтам — все допустимые
символы ASCII). Неверное значение не переносится в ответ и журнал:
генерируется новое (`crypto/rand`, 16 байт, hex — 32 символа), итоговое
возвращается заголовком `X-Request-ID` и попадает в контекст запроса
(`context.WithValue` с непубличным типом ключа). Порядок middleware:
`requestID(requestLog(mux))` — журнал внутренний, поэтому видит
идентификатор в контексте.

Событие приёма задачи журналируется с полями:

```go
h.logger.InfoContext(r.Context(), "job accepted",
    "request_id", requestID,
    "body_bytes", len(body), // фактически прочитанные байты io.ReadAll
    "duration_ms", time.Since(started).Milliseconds(),
)
```

`body_bytes` — `len` результата `io.ReadAll`, а не заголовок Content-Length
(раздел 2.5/вариант B: заголовку доверять нельзя). Общий `requestLog` тоже
включает `request_id`.

Фактические curl-сессии реального запуска (`LOG_LEVEL=info`,
`SHUTDOWN_TIMEOUT=10s`, MAX_BODY_BYTES по умолчанию):


### 4.4. Пункт 4 — тесты 413 и 503, точка принятия операции

- `TestJobsTooLargeSlightly`: предел 64, тело 65 байт → 413
  `{"error":"request body exceeds MAX_BODY_BYTES","limit_bytes":64}`;
- `TestJobsTooLargeMassively`: предел 64, тело 64000 байт → 413;
- `TestJobsNotReadyRejectsBeforeReadingBody`: `SetReady(false)` + тело
  64000 байт при пределе 64 → **503, а не 413**. Тело больше предела,
  но ответ — отказ допуска: доказательство, что проверка готовности
  выполняется ДО чтения тела (первая операция обработчика; журнал не
  содержит ни «job accepted», ни «job body too large»).

Точка принятия операции зафиксирована комментарием в коде `jobs`:
решение принимается один раз по текущему состоянию флага; работа, уже
допущенная до смены флага, не становится новой. Это же показывает
интеграционный тест 2: запрос, допущенный до `SetReady(false)`, завершается
202 уже во время остановки.

Фактический 413 из реального запуска (тело 2097152 байта > 1048576):

### 4.5. Пункт 5 — опыт остановки во время медленной загрузки тела

**(а) Интеграционный тест в процессе** (`lifecycle_test.go`): настоящий
`net.Listener` на `127.0.0.1:0`, настоящий `http.Client`; клиент в горутине
отправляет POST /jobs с телом меньше предела, но пишет его медленно —
кастомный `slowBodyReader` отдаёт порции с паузами. Тест 1: тело 2048 байт
(предел 4096), порции 16 байт × пауза 100 мс — передача ~12.8 с; бюджет
остановки 1 с. `Shutdown` возвращает `context.DeadlineExceeded` — ожидание
не закончилось, пока клиент не завершил передачу. После исчерпания бюджета
канал результата клиента остаётся пуст ≥300 мс: запрос продолжал читаться,
т.е. `MaxBytesReader` сам чтение не прекращает (размер не превышен).
Механизм, завершивший чтение, зафиксирован в тесте логом: «reading was
terminated by test-side client cancellation; in a real deployment — by
process exit after the Shutdown error». Тест 2 (сопоставление величин):
тело 80 байт, передача ~1.5 с, бюджет 5 с — `Shutdown` возвращает nil,
допущенный запрос получает 202 уже во время остановки.

```
=== RUN   TestShutdownTimesOutDuringSlowBodyUpload
    lifecycle_test.go:182: reading was terminated by test-side client cancellation; in a real deployment — by process exit after the Shutdown error
--- PASS: TestShutdownTimesOutDuringSlowBodyUpload (1.55s)
=== RUN   TestShutdownWaitsForSlowBodyUploadCompletion
--- PASS: TestShutdownWaitsForSlowBodyUploadCompletion (1.82s)
```

**(б) Реальный запуск**: собран `order-command.exe`, запущен с
`LOG_LEVEL=info`, `SHUTDOWN_TIMEOUT=10s`, `MAX_BODY_BYTES` по умолчанию.
Факты: GET /livez → 200, GET /readyz → 200, POST /jobs с малым телом →
202 + заголовок X-Request-ID + строка «job accepted» с
request_id/body_bytes/duration_ms; POST с телом 2 MiB → 413; POST с
невалидным X-Request-ID → подстановка нового. Медленная загрузка:
тело 16384 байта (< предела), `curl.exe --limit-rate 1K --max-time 8` —
полная передача заняла бы ~16 с, клиент оборван через 8 с; ответа клиент
не получил (`http_code=000` — индикатор отсутствия ответа, не HTTP-код),
сервер всё это время находился в чтении:

```
> curl.exe -s -o NUL -w "http_code=%{http_code}\n" --limit-rate 1K --max-time 8 -X POST --data-binary @payload-16k.bin http://localhost:8080/jobs
http_code=000
```

```
{"time":"2026-10-05T00:20:57.6787788+03:00","level":"WARN","msg":"job body read failed","request_id":"4c467c392025e3af13e5875205dd37f8","error":"unexpected EOF"}
{"time":"2026-10-05T00:20:57.6798193+03:00","level":"INFO","msg":"http request completed","method":"POST","path":"/jobs","request_id":"4c467c392025e3af13e5875205dd37f8","duration_ms":8014}
```

Здесь чтение завершил обрыв клиента по `--max-time`: сервер при
незавершённой передаче и достаточном бюджете просто ждёт. Windows-оговорка:
graceful-остановку сигналом из скрипта на Windows не отправить, имитация
Ctrl+C через taskkill не выполнялась (процесс убран принудительно
Stop-Process только для освобождения порта после опыта); путь остановки
`SetReady(false) → Shutdown → deadline exceeded → выход процесса`
подтверждается интеграционным тестом. Практика это допускает: Linux-контейнер
и Kubernetes не обязательны.

**(в) Эксперимент зафиксирован** в `docs/experiments/01-lifecycle.md` по
шаблону раздела 3.6 (Условие/Ожидание/Наблюдение/Вывод) с сопоставлением
размера (16384 и 2048 байт < пределов), скорости (1 КБ/с curl, 16 байт/100 мс
в тесте) и бюджетов (1 с / 5 с / 10 с); явно указано, какой механизм завершил
чтение в каждом случае; отмечено, что ограничение размера НЕ является защитой
от медленной загрузки, а `MAX_BODY_BYTES`, `SHUTDOWN_TIMEOUT` и сетевые сроки
(`ReadTimeout` и т.п.) — независимые ограничения; сетевые сроки чтения тела
в каркас не добавлялись (установлены только ReadHeaderTimeout 2s и
IdleTimeout 60s), что зафиксировано как ограничение.

  ReadHeaderTimeout/IdleTimeout, /livez//readyz//slow) — код проекта;
- `MAX_BODY_BYTES` (по умолчанию 1 MiB = 1048576) с тремя различаемыми
  классами ошибок — тесты + фактические отказы запуска с exit=1;
- `POST /jobs` с обязательным чтением тела через `MaxBytesReader` +
  `io.ReadAll` и проверкой ошибки (`errors.As` по `*http.MaxBytesError`
  с резервным сравнением строки для старых версий) — curl-факты 202 и 413
  (+limit_bytes), тесты на небольшое и многократное превышение;
- идентификатор запроса по контракту 8–64/[A-Za-z0-9_-] с генерацией
  crypto/rand-hex, возвратом в заголовке и контекстом; журнал «job accepted»
  с request_id/body_bytes/duration_ms, где body_bytes — фактические байты, —
  тест с ложным Content-Length и строки run1.log;
- отказ 503 при отрицательной готовности ДО чтения тела с зафиксированной
  точкой принятия операции — тест (тело больше предела → 503, не 413) и
  поведение допущенного запроса в интеграционном тесте 2;
- опыт остановки во время медленной загрузки — интеграционные тесты
  (недостаточный/достаточный бюджет, зафиксирован механизм завершения
  чтения) и реальный запуск с `--limit-rate` (сервер ждёт ~8 с до обрыва
  клиента, 000 у curl, «job body read failed»: unexpected EOF); документ
  `docs/experiments/01-lifecycle.md`.

Честные ограничения: очередь задач не реализована — 202 демонстрирует
форму асинхронного интерфейса, долговечное принятие не гарантируется;
`LOG_LEVEL` разбирается мягко (неизвестное значение молча становится
info — унаследовано от базового каркаса и не скрыто); код ответа в
`requestLog` не журналируется; сетевые сроки чтения тела (ReadTimeout/
SetReadDeadline) не добавлялись — защиты от медленной загрузки на уровне
транспорта нет, `MAX_BODY_BYTES` её не заменяет; graceful-остановка
сигналом в Windows-скрипте не проверялась (подтверждена интеграционным
тестом); Docker/Kubernetes и поведение платформенной маршрутизации не
проверялись; строгое измерение «время от сигнала до выхода процесса»
в реальном запуске не выполнялось — соответствующие интервалы получены
только внутри интеграционных тестов.
