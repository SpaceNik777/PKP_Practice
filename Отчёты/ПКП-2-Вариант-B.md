## 1. Введение

Правило, записанное прямо в обработчике HTTP-запроса или спрятанное
в SQL-запросе, почти незаметно, пока у операции один вход. Как только
появляется второй вход (обработчик сообщений Kafka, ночная пакетная
загрузка), правило приходится переписывать заново — и две копии
неизбежно расходятся: одну поправили, о второй забыли. Система начинает
вести себя по-разному в зависимости от пути, которым пришёл запрос.

У такого размещения правил есть и вторая цена — стоимость проверки:
чтобы протестировать условие «количество товара должно быть
положительным» или «интервал резерва должен быть корректным»,
приходится поднимать веб-сервер, базу данных или брокера. Тест
становится медленным, хрупким и требует окружения, которое к самому
правилу отношения не имеет.

Оба несчастья лечатся одним перемещением: правила переезжают в
предметную область — типы и разрешённые переходы, — а инфраструктура
(HTTP, хранилище, брокер) подключается к зафиксированному поведению
как адаптеры. Практическая выгода измерима: тесты правил идут доли
секунды без внешнего окружения, а замена технологии не затрагивает
ни один файл предметной области.

## 4. Реализация по шагам

### 4.1. Пакет `order` по разбору (разделы 3.1–3.6)

**Ключевые решения.**

- **Закрытые поля.** Единственный способ получить заказ — конструктор
  `New`, который не возвращает объект, не прошедший проверки. Поэтому
  в системе не может появиться подтверждённый пустой заказ: такое
  состояние недостижимо через открытый интерфейс.

```go
type Order struct {
	id      string
	version int64
	status  Status
	lines   []Line
}
```

- **Центы `int64`.** `float64` не представляет десятичные дроби точно;
  целые числа в минимальных единицах избавляют от класса ошибок
  полностью.

```go
type Line struct {
	SKU       string
	Quantity  int
	UnitCents int64
}
```

- **Копирование срезов.** Срез в Go — описатель общего массива:
  сохранение переданного извне среза или выдача внутреннего наружу
  позволяет менять агрегат в обход проверок. Конструктор копирует,
  `Lines()` возвращает копию:

```go
copied := make([]Line, len(lines))
copy(copied, lines)
...
func (o Order) Lines() []Line {
	copied := make([]Line, len(o.lines))
	copy(copied, o.lines)
	return copied
}
```

- **Ошибки-маркеры с `%w`.** Класс результата — часть контракта;
  обёртка сохраняет первопричину для `errors.Is`, а транспортный
  адаптер позже сопоставит `ErrInvalid`→422, `ErrConflict`→409,
  `ErrNotFound`→404:

```go
var (
	ErrInvalid  = errors.New("invalid order")
	ErrConflict = errors.New("order conflict")
	ErrNotFound = errors.New("order not found")
)
...
if line.Quantity <= 0 {
	return Order{}, fmt.Errorf("%w: line %d quantity must be positive", ErrInvalid, i)
}
```

- **Получатели на значении, переход на указателе.** `Confirm()`
  допустим только из PENDING и наращивает `version` (заготовка
  оптимистичной блокировки):

```go
func (o *Order) Confirm() error {
	if o.status != StatusPending {
		return fmt.Errorf("%w: cannot confirm from %s", ErrConflict, o.status)
	}
	o.status = StatusConfirmed
	o.version++
	return nil
}
```

- **Порт на стороне потребителя, служба без правил.** В `Service.Create`
  нет ни проверок (они в `New`), ни ветвлений по хранилищу, ни формата
  ответа — только порядок шагов; ошибка хранилища оборачивается
  контекстом операции:

```go
if err := s.repository.Create(ctx, value); err != nil {
	return Created{}, fmt.Errorf("create order %s: %w", value.ID(), err)
}
```

- **Адаптер в памяти.** `sync.RWMutex` (чтения параллельны, запись
  исключительна); проверка+вставка под одной блокировкой; `ctx.Err()`
  в начале операций; значения по значению; `var _ order.Repository =
  (*Repository)(nil)` — ошибка несовместимости всплывёт прямо в файле
  адаптера.

### 4.2. Вариант B: агрегат Reservation (все 5 пунктов)

#### Пункт 1. Агрегат с интервалом [from, to), запрет пустого ресурса и to <= from

`internal/reservation/domain.go`. Резерв занимает ресурс на
**полуоткрытом интервале** `[From, To)`: момент `From` включён, момент
`To` уже свободен. Полуоткрытость — не вкусовое решение: она снимает
пограничный конфликт, когда резерв до 12:00 и резерв с 12:00 должны
соседствовать, не пересекаясь. Поля закрыты; геттеры объявлены на
значении; начальный статус — `ACTIVE`, `version = 1`. Конструктор
отклоняет пустой id, пустой ресурс и неверный интервал (`to <= from`),
каждое нарушение — отдельной причиной внутри класса `ErrInvalid`:

```go
func New(id string, resource string, from time.Time, to time.Time) (Reservation, error) {
	if id == "" {
		return Reservation{}, fmt.Errorf("%w: empty id", ErrInvalid)
	}
	if resource == "" {
		return Reservation{}, fmt.Errorf("%w: empty resource", ErrInvalid)
	}
	if !to.After(from) {
		return Reservation{}, fmt.Errorf("%w: interval [%s, %s) must have to > from", ErrInvalid, from.Format(time.RFC3339), to.Format(time.RFC3339))
	}

	return Reservation{
		id:       id,
		resource: resource,
		from:     from,
		to:       to,
		status:   StatusActive,
		version:  1,
	}, nil
}
```

Полезный метод-запрос `Overlaps` кодирует пересечение полуоткрытых
интервалов `from < other.to && other.from < to` — чистая функция,
пригодится службе расписания для обоснования границы с занятостью:

```go
func (r Reservation) Overlaps(other Reservation) bool {
	return r.from.Before(other.to) && other.from.Before(r.to)
}
```

Табличный тест `TestNewValidatesInput` покрывает пустой id, пустой
ресурс, `to == from` и `to < from` → `ErrInvalid`; отдельный тест
фиксирует начальное состояние ACTIVE/version=1 и значения геттеров.

#### Пункт 2. Переход Cancel только из ACTIVE + тест повторного вызова

Переход объявлен на указателе (изменяет состояние), из любого
состояния, кроме ACTIVE, — конфликт:

```go
func (r *Reservation) Cancel() error {
	if r.status != StatusActive {
		return fmt.Errorf("%w: cannot cancel from %s", ErrConflict, r.status)
	}
	r.status = StatusCancelled
	r.version++
	return nil
}
```

**Выбор контракта повторного вызова — КОНФЛИКТНЫЙ** (повторный `Cancel`
уже отменённого резерва возвращает `ErrConflict`, а не «успех без
изменений»). Обоснование зафиксировано в комментарии к методу:

- симметрия с `Confirm` из разбора: повторный вызов — ошибка
  состояния, а не новый результат;
- жёсткая семантика честнее выявляет потерянные обновления
  вызывающей стороны: клиент, не знающий о первой отмене, получает
  `ErrConflict`, а не молчаливое подтверждение своей картины мира;
- идемпотентность, если она понадобится транспортному адаптеру
  (например, повторная доставка сообщения), реализуется на его
  стороне — предварительным чтением статуса или подавлением
  конкретного класса ошибки.

Обязательный тест повторного вызова (`TestCancelCannotBeCalledTwice`):
первый `Cancel` — успех (CANCELLED, version выросла), второй —
`errors.Is(err, ErrConflict)`. Проверка через `errors.Is` устойчива
к изменению текста сообщения.

#### Пункт 3. Минимальный порт хранения + безопасный memory-адаптер

Порт объявлен в `internal/reservation/service.go` (потребитель), а не
в адаптере. Сценарий `Cancel` потребовал сохранения изменённого
агрегата, поэтому порт содержит метод `Save`:

```go
type Repository interface {
	Create(ctx context.Context, value Reservation) error
	ByID(ctx context.Context, id string) (Reservation, error)
	Save(ctx context.Context, value Reservation) error
}
```

Адаптер `internal/reservation/memory/repository.go`: `sync.RWMutex`,
`map[string]reservation.Reservation`, `ctx.Err()` в начале каждой
операции, дубликат → `reservation.ErrConflict`, отсутствие →
`fmt.Errorf("%w: %s", reservation.ErrNotFound, id)`, `Save` обновляет
только существующую запись (иначе — `ErrNotFound`: Save не может
изобрести агрегат). Рядом с типом — статическая проверка
соответствия порту:

```go
var _ reservation.Repository = (*Repository)(nil)
```

**Проверку пересечения интервалов в адаптер добавлять нельзя** —
и мы её не добавили: занятость слотов — ответственность расписания,
а не хранилища резервов (см. ADR в пункте 5). Хранилище хранит
и извлекает агрегаты по идентичности; накрепко связав его с логикой
занятости, мы лишили бы себя возможности заменить его на PostgreSQL
без переписывания правил.

#### Пункт 4. Служба Create/Cancel с отдельными результатами

`Service.Create` строит агрегат конструктором `New`, сохраняет
и возвращает `Created{ID, Resource, From, To, Status, Version}` —
не раскрывая агрегат. `Service.Cancel` координирует шаги сценария:
прочитать → перейти → сохранить; каждый сбой оборачивается контекстом
операции через `%w`, поэтому класс ошибки сохраняется для `errors.Is`:

```go
func (s *Service) Cancel(ctx context.Context, id string) (Cancelled, error) {
	if id == "" {
		return Cancelled{}, fmt.Errorf("%w: empty id", ErrInvalid)
	}
	value, err := s.repository.ByID(ctx, id)
	if err != nil {
		return Cancelled{}, fmt.Errorf("cancel reservation %s: %w", id, err)
	}
	if err := value.Cancel(); err != nil {
		return Cancelled{}, fmt.Errorf("cancel reservation %s: %w", value.ID(), err)
	}
	if err := s.repository.Save(ctx, value); err != nil {
		return Cancelled{}, fmt.Errorf("cancel reservation %s: %w", value.ID(), err)
	}
	return Cancelled{
		ID:      value.ID(),
		Status:  value.Status(),
		Version: value.Version(),
	}, nil
}
```

`Create` оборачивает ошибку хранилища как `"create reservation %s: %w"`.
Результаты — отдельные объекты `Created` и `Cancelled`: вызывающий
получает ровно то, что нужно показать, и не приобретает возможности
воздействовать на состояние.

#### Пункт 5. ADR: граница расписания и резервирования

Полный текст: `docs/adr/0001-schedule-reservation-boundary.md`.

Сводка. **Контекст**: расписание (календарь занятости слотов ресурса)
выглядит отдельной обязанностью. По теории владение решает: истинное
состояние занятости — агрегированный факт обо всех резервах, которым
не владеет ни один отдельный резерв; это прямой аналог склада из
раздела 2.2 («заказ не может гарантировать то, чем не владеет»).
Локальные инварианты резерва — корректность собственного интервала
и допустимость перехода; непересечение с другими резервами —
межагрегатный факт, который нельзя удерживать внутри одного агрегата.
**Решение**: сейчас один модуль `reservation`, владеющий только
жизненным циклом резерва (создание/отмена); `Overlaps` — чистая
функция домена; хранилище пересечения не проверяет. Отдельная служба
расписания появится при подключении реального конфликта интервалов —
через порт, объявленный на стороне потребителя. **Последствия**:
малый агрегат и быстрые тесты; взаимозаменяемость хранилищ;
принимаемый компромисс — до появления расписания два резерва на один
слот технически могут быть созданы оба; атомарность «проверка
занятости + создание» обеспечит служба расписания. **Критерии
пересмотра границы**: реальный конфликт интервалов; несколько
ресурсов с независимыми календарными правилами; второй вход
(Kafka, пакетная загрузка); нагрузка проверки занятости. Пересмотр
оформляется новой записью ADR.

## 5. Вывод

Реализовано и чем подтверждено:

- **Пакет `order` по разбору 3.1–3.6**: агрегат с закрытыми полями,
  центы `int64`, копирование срезов, ошибки-маркеры с `%w`, переход
  `Confirm`, порт на стороне потребителя, memory-адаптер с RWMutex,
  служба `Create/ByID`, тесты — 5 функций (10 PASS-строк вместе
  с подтестами), `ok ... 0.293s` (свежий прогон 0.366 с).
- **Вариант B, все 5 пунктов**: (1) агрегат `Reservation` с
  полуоткрытым интервалом `[from, to)` и запретом пустых id/ресурса
  и `to <= from` → `ErrInvalid` (табличный тест, включая границы
  `to == from` и `to < from`); (2) `Cancel` только из ACTIVE,
  **контракт повторного вызова — конфликтный**: повторная отмена →
  `ErrConflict` «cannot cancel from %s» (обязательный тест;
  обоснование — симметрия с `Confirm`, жёсткая семантика ошибки
  состояния, идемпотентность — забота вызывающей стороны);
  (3) порт `reservation.Repository` (`Create/ByID/Save`) у потребителя +
  безопасный при одновременном доступе memory-адаптер со статической
  проверкой `var _ reservation.Repository = (*Repository)(nil)` —
  без проверки пересечений интервалов; (4) служба `Create`/`Cancel`
  с обёртками `"create reservation %s: %w"` /
  `"cancel reservation %s: %w"` и отдельными результатами
  `Created`/`Cancelled`, не раскрывающими агрегат; (5) ADR 0001 —
  занятость слотов принадлежит расписанию, резерв владеет только
  своим жизненным циклом, служба расписания через порт в будущем,
  критерии пересмотра.
- **Полуоткрытость подтверждена тестами `Overlaps`**: соседние
