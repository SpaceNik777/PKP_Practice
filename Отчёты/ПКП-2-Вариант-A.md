## 1. Введение

Правило, записанное прямо в обработчике HTTP-запроса или спрятанное
в SQL-запросе, почти незаметно, пока у операции один вход. Как только
появляется второй вход (обработчик сообщений Kafka, ночная пакетная
загрузка), правило приходится переписывать заново — и две копии
неизбежно расходятся: одну поправили, о второй забыли. Система начинает
вести себя по-разному в зависимости от пути, которым пришёл запрос.

У такого размещения правил есть и вторая цена — стоимость проверки:
чтобы протестировать условие «количество товара должно быть
положительным», приходится поднимать веб-сервер, базу данных или
брокера. Тест становится медленным, хрупким и требует окружения,
которое к самому правилу отношения не имеет.

Оба несчастья лечатся одним перемещением: правила переезжают в
предметную область — типы и разрешённые переходы, — а инфраструктура
(HTTP, хранилище, брокер) подключается к зафиксированному поведению
как адаптеры. Практическая выгода измерима: тесты правил идут доли
секунды без внешнего окружения, а замена технологии не затрагивает
ни один файл предметной области.

## 4. Реализация по шагам

### 4.1. Пакет `order` по разбору (разделы 3.1–3.6)

**Ключевые решения.**

- **Закрытые поля.** Единственный способ получить заказ — конструктор
  `New`, который не возвращает объект, не прошедший проверки. Поэтому
  в системе не может появиться подтверждённый пустой заказ: такое
  состояние недостижимо через открытый интерфейс.

```go
type Order struct {
	id      string
	version int64
	status  Status
	lines   []Line
}
```

- **Центты `int64`.** `float64` не представляет десятичные дроби точно;
  целые числа в минимальных единицах избавляют от класса ошибок
  полностью.

```go
type Line struct {
	SKU       string
	Quantity  int
	UnitCents int64
}
```

- **Копирование срезов.** Срез в Go — описатель общего массива:
  сохранение переданного извне среза или выдача внутреннего наружу
  позволяет менять агрегат в обход проверок. Конструктор копирует,
  `Lines()` возвращает копию:

```go
copied := make([]Line, len(lines))
copy(copied, lines)
...
func (o Order) Lines() []Line {
	copied := make([]Line, len(o.lines))
	copy(copied, o.lines)
	return copied
}
```

- **Ошибки-маркеры с `%w`.** Класс результата — часть контракта;
  обёртка сохраняет первопричину для `errors.Is`, а транспортный
  адаптер позже сопоставит `ErrInvalid`→422, `ErrConflict`→409,
  `ErrNotFound`→404:

```go
var (
	ErrInvalid  = errors.New("invalid order")
	ErrConflict = errors.New("order conflict")
	ErrNotFound = errors.New("order not found")
)
...
if line.Quantity <= 0 {
	return Order{}, fmt.Errorf("%w: line %d quantity must be positive", ErrInvalid, i)
}
```

- **Получатели на значении, переход на указателе.** `Confirm()`
  допустим только из PENDING и наращивает `version` (заготовка
  оптимистичной блокировки):

```go
func (o *Order) Confirm() error {
	if o.status != StatusPending {
		return fmt.Errorf("%w: cannot confirm from %s", ErrConflict, o.status)
	}
	o.status = StatusConfirmed
	o.version++
	return nil
}
```

- **Порт на стороне потребителя, служба без правил.** В `Service.Create`
  нет ни проверок (они в `New`), ни ветвлений по хранилищу, ни формата
  ответа — только порядок шагов; ошибка хранилища оборачивается
  контекстом операции:

```go
if err := s.repository.Create(ctx, value); err != nil {
	return Created{}, fmt.Errorf("create order %s: %w", value.ID(), err)
}
```

- **Адаптер в памяти.** `sync.RWMutex` (чтения параллельны, запись
  исключительна); проверка+вставка под одной блокировкой; `ctx.Err()`
  в начале операций; значения по значению; `var _ order.Repository =
  (*Repository)(nil)` — ошибка несовместимости всплывёт прямо в файле
  адаптера.

### 4.2. Вариант A: агрегат Application (все 5 пунктов)

#### Пункт 1. Агрегат со статусом DRAFT, запрет пустого автора и темы

`internal/application/domain.go`. Статусы: `DRAFT`, `SUBMITTED` и
`REJECTED` — последний объявлен в словаре предметной области без
перехода к нему (как `StatusRejected` в разборе `order`). Поля закрыты;
срезов нет (строковые поля), копировать нечего — но и напрямую поля
извне недоступны. Каждое нарушение инварианта названо отдельной
причиной внутри класса `ErrInvalid`:

```go
func New(id, author, topic string) (Application, error) {
	if id == "" {
		return Application{}, fmt.Errorf("%w: empty id", ErrInvalid)
	}
	if author == "" {
		return Application{}, fmt.Errorf("%w: empty author", ErrInvalid)
	}
	if topic == "" {
		return Application{}, fmt.Errorf("%w: empty topic", ErrInvalid)
	}

	return Application{
		id:      id,
		author:  author,
		topic:   topic,
		status:  StatusDraft,
		version: 1,
	}, nil
}
```

Табличный тест (`TestNewValidatesFields`) покрывает пустой id,
пустого автора, пустую тему → `ErrInvalid`; отдельные тесты фиксируют
начальное состояние DRAFT/version=1 и значения геттеров.

#### Пункт 2. Переход Submit только из DRAFT + тест повторной отправки

Переход объявлен на указателе (изменяет состояние), из любого состояния,
кроме DRAFT, — конфликт:

```go
func (a *Application) Submit() error {
	if a.status != StatusDraft {
		return fmt.Errorf("%w: cannot submit from %s", ErrConflict, a.status)
	}
	a.status = StatusSubmitted
	a.version++
	return nil
}
```

Обязательный тест повторной отправки (`TestSubmitCannotBeRepeated`):
первый `Submit` — успех (SUBMITTED, version 2), второй — `errors.Is(err,
ErrConflict)`. Проверка через `errors.Is` устойчива к изменению текста
сообщения.

#### Пункт 3. Порт на стороне прикладного пакета + безопасный memory-адаптер

Порт объявлен в `internal/application/service.go` (потребитель), а не
в адаптере. Сценарий `Submit` потребовал сохранения изменённого
агрегата, поэтому порт вырос методом `Save` — это нормальная эволюция
порта: он остался минимально достаточным для потребителя:

```go
type Repository interface {
	Create(ctx context.Context, value Application) error
	ByID(ctx context.Context, id string) (Application, error)
	Save(ctx context.Context, value Application) error
}
```

Адаптер `internal/application/memory/repository.go`: `sync.RWMutex`,
`map[string]application.Application`, `ctx.Err()` в начале каждой
операции, дубликат → `application.ErrConflict`, отсутствие →
`fmt.Errorf("%w: %s", application.ErrNotFound, id)`, `Save` обновляет
только существующую запись (иначе — `ErrNotFound`: Save не может
изобрести агрегат). Рядом с типом — статическая проверка
соответствия порту:

```go
var _ application.Repository = (*Repository)(nil)
```

#### Пункт 4. Служба Create/Submit с контекстом в ошибках

`Service.Create` строит агрегат, сохраняет, возвращает `Created`
(ID, Status, Version) — не раскрывая агрегат. `Service.Submit`
координирует шаги сценария; каждый сбой оборачивается контекстом
операции через `%w`, поэтому класс ошибки сохраняется для `errors.Is`:

```go
func (s *Service) Submit(ctx context.Context, id string) (SubmitResult, error) {
	if id == "" {
		return SubmitResult{}, fmt.Errorf("%w: empty id", ErrInvalid)
	}

	value, err := s.repository.ByID(ctx, id)
	if err != nil {
		return SubmitResult{}, fmt.Errorf("submit application %s: %w", id, err)
	}

	if err := value.Submit(); err != nil {
		return SubmitResult{}, fmt.Errorf("submit application %s: %w", id, err)
	}

	if err := s.repository.Save(ctx, value); err != nil {
		return SubmitResult{}, fmt.Errorf("submit application %s: %w", id, err)
	}

	return SubmitResult{
		ID:      value.ID(),
		Status:  value.Status(),
		Version: value.Version(),
	}, nil
}
```

`Create` оборачивает ошибку хранилища как `"create application %s: %w"`.
Результаты — отдельные объекты `Created` и `SubmitResult`: вызывающий
получает ровно то, что нужно показать, и не приобретает возможности
воздействовать на состояние.

#### Пункт 5. ADR: граница согласования и уведомлений

Полный текст: `docs/adr/0001-approval-notifications-boundary.md`.

Сводка. **Контекст**: уведомления (автору — «принята», согласующим —
«требуется решение») выглядят отдельной обязанностью; по разделу 2.6
граница определяется тремя вопросами — меняются ли части вместе, нужна
ли общая транзакция, один ли владелец. **Решение**: на текущем этапе
согласование и уведомления остаются одним модулем (модульный
монолит `internal/application`); когда уведомления понадобятся, они
войдут через порт, объявленный на стороне потребителя, а доставщик
(e-mail, брокер) будет адаптером в точке сборки зависимостей — правила
заявки не изменятся. **Обоснование**: распределение — способ купить
независимость, а не навести порядок; пока модули меняются вместе,
живут в одном процессе и принадлежат одному владельцу, вынесение
добавит задержку и отказы по сети, но не даст независимости.
**Последствия и критерии пересмотра**: пересмотр по измеримым фактам —
второй вход (например, Kafka как потребитель событий о заявках),
разные причины изменений (правила стабильны, доставка меняется часто),
отдельный владелец, нагрузка доставки, влияющая на доступность
согласования. Пересмотр оформляется новой записью ADR.

## 5. Вывод

Реализовано и чем подтверждено:

- **Пакет `order` по разбору 3.1–3.6**: агрегат с закрытыми полями,
  центы `int64`, копирование срезов, ошибки-маркеры с `%w`, переход
  `Confirm`, порт на стороне потребителя, memory-адаптер с RWMutex,
  служба `Create/ByID`, тесты — 5 функций (10 PASS-строк вместе
  с подтестами), `ok ... 0.278s`.
- **Вариант A, все 5 пунктов**: (1) агрегат `Application` со статусом
  DRAFT и запретом пустых id/автора/темы → `ErrInvalid` (табличный
  тест); (2) `Submit` только из DRAFT, повторная отправка →
  `ErrConflict` (обязательный тест); (3) порт `application.Repository`
  у потребителя + безопасный при одновременном доступе memory-адаптер
  со статической проверкой `var _ application.Repository =
  (*Repository)(nil)`; (4) служба `Create`/`Submit` с обёртками
  `"create application %s: %w"` / `"submit application %s: %w"`,
  эволюция порта методом `Save`, результаты `Created`/`SubmitResult`
  без раскрытия агрегата; (5) ADR 0001 — один модуль сейчас,
  уведомления через порт в будущем, критерии пересмотра.
- **Быстрые тесты без окружения**: application 0.249–0.279 с, order
  0.278–0.409 с — доли секунды, ни сети, ни базы данных.
- **Направление зависимостей**: `go list` подтверждает, что
  `internal/application` и `internal/order` импортируют только
  `[context errors fmt]`; адаптеры импортируют домен, обратного
  пути нет.
- **Качество**: `go fmt` (канонический формат), `go vet` (чисто),
  `go test ./...` и `go test -race ./...` — все пакеты ok, включая
  перенос из работы 1 (config, httpserver); ничего не сломано.
- **Git**: репозиторий с одним итоговым коммитом `701e0ed`.

Ограничения (осознанные рамки варианта): HTTP-вход для `Application`
не подключался — вариант этого не требовал, сценарии вызывались
тестами как вторым полноценным входом; миграция на PostgreSQL
  не выполнялась — взаимозаменяемость хранилищ обеспечена портом:
  замена memory-адаптера на SQL не затронет ни файл домена, ни файл
  службы.
