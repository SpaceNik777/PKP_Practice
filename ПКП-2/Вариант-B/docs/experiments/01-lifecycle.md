# Эксперимент: остановка во время медленной загрузки тела (вариант B)

## Условие

ОС: Windows 10 Pro (22H2), shell cmd.exe. Go: go1.26.8 windows/amd64.

Два источника наблюдений, дополняющие друг друга:

1. Интеграционный тест в процессе (`lifecycle_test.go`, настоящий
   `net.Listener` на `127.0.0.1:0`, настоящий `http.Client`):
   - тест 1 «недостаточный бюджет»: тело 2048 байт при пределе
     `MAX_BODY_BYTES=4096`, передача порциями по 16 байт с паузой
     100 мс — полная передача ~12.8 с; бюджет остановки 1 с;
   - тест 2 «достаточный бюджет»: тело 80 байт при том же пределе,
     10 порций по 8 байт с паузой 150 мс (~1.5 с); бюджет 5 с.
   Сигнал остановки моделируется вызовом `SetReady(false)` +
   `server.Shutdown(ctx)` — теми же операциями, что выполняет `run()`
   после отмены корневого контекста сигналом.
2. Реальный запуск собранного `order-command.exe`
   (`LOG_LEVEL=info`, `SHUTDOWN_TIMEOUT=10s`, `MAX_BODY_BYTES`
   по умолчанию — 1048576, адрес `:8080`) и curl.exe:
   `POST /jobs` с телом 16384 байта при `--limit-rate 1K`
   (полная передача ~16 с) и `--max-time 8` — клиент обрывает
   передачу через 8 с.

ReadTimeout и иные сетевые сроки чтения тела на сервере НЕ заданы
(см. раздел 2.6 практики): в каркасе установлены только
`ReadHeaderTimeout: 2s` и `IdleTimeout: 60s`, срока чтения тела нет.

## Ожидание

Клиент, не превышающий `MAX_BODY_BYTES`, может писать тело дольше
бюджета остановки: `MaxBytesReader` ограничивает объём, но не
длительность передачи. Поэтому:

- при бюджете 1 с и остатке передачи ~12.5 с `Shutdown` вернёт
  `context deadline exceeded` — ожидание не закончилось, пока клиент
  не завершил передачу;
- чтение завершит НЕ `MaxBytesReader`: в реальном развёртывании —
  выход процесса после ошибки `Shutdown` (run возвращает ошибку,
  main вызывает os.Exit); в интеграционном тесте — отмена
  клиентского контекста самим тестом;
- при бюджете 5 с и остатке передачи ~1.5 с `Shutdown` дождётся
  завершения, запрос получит `202 Accepted` уже во время остановки
  (точка принятия операции пройдена до `SetReady(false)`);
- в curl-опыте без сигнала остановки сервер просто ждёт клиента;
  после обрыва клиента по `--max-time` чтение завершится ошибкой,
  ответа клиент не получит (`000` у curl — не HTTP-код).

## Наблюдение

Интеграционный тест (`go test -v -run 'TestShutdown.*SlowBodyUpload'`):

```
=== RUN   TestShutdownTimesOutDuringSlowBodyUpload
    lifecycle_test.go:182: reading was terminated by test-side client cancellation; in a real deployment — by process exit after the Shutdown error
--- PASS: TestShutdownTimesOutDuringSlowBodyUpload (1.55s)
=== RUN   TestShutdownWaitsForSlowBodyUploadCompletion
--- PASS: TestShutdownWaitsForSlowBodyUploadCompletion (1.82s)
```

Факты внутри теста 1: `Shutdown` с бюджетом 1 с вернул
`context.DeadlineExceeded`; после исчерпания бюджета канал результата
клиента оставался пуст ещё ≥300 мс — запрос продолжал читаться, т.е.
`MaxBytesReader` (объём 2048 < 4096) чтение не прекратил. Чтение
завершила отмена клиентского контекста тестом (модель выхода
процесса). В тесте 2 `Shutdown` вернул nil, клиент получил 202.

Реальный запуск, curl (вывод сокращён до значимых строк):

```
> curl.exe -s -o NUL -w "http_code=%{http_code}\n" --limit-rate 1K --max-time 8 -X POST --data-binary @payload-16k.bin http://localhost:8080/jobs
http_code=000
```

Журнал сервера (run1.log) — сервер ждал до обрыва клиента:

```
{"time":"2026-10-05T00:20:57.6787788+03:00","level":"WARN","msg":"job body read failed","request_id":"4c467c392025e3af13e5875205dd37f8","error":"unexpected EOF"}
{"time":"2026-10-05T00:20:57.6798193+03:00","level":"INFO","msg":"http request completed","method":"POST","path":"/jobs","request_id":"4c467c392025e3af13e5875205dd37f8","duration_ms":8014}
```

duration_ms=8014: от входа запроса до обрыва клиентом прошло ~8 c,
всё это время сервер находился в чтении тела (16384 < 1048576).
Ответа клиент не получил; 000 у curl — индикатор отсутствия ответа,
а не HTTP-код.

Сопоставление величин: размер 16384 байта < предел 1048576 байт;
скорость 1 КБ/с; полная передача ~16 с >> --max-time 8 с (curl-опыт)
и ~12.8 с >> 1 с бюджета (тест).

## Вывод

Результат определяется остатком работы на момент остановки и
бюджетом, а не одним лишь `MAX_BODY_BYTES`: 5 с > 1.5 с — успешное
осушение и 202; 1 с < 12.5 с — `Shutdown` возвращает
`context deadline exceeded`, чтение продолжается.

Механизм, завершивший чтение при недостаточном бюджете, зафиксирован:
в тесте — отмена клиентского контекста самим тестом; в реальном
развёртывании — выход процесса после ошибки `Shutdown`. `MaxBytesReader`
медленную передачу в пределах размера не останавливает: ограничение
размера НЕ является защитой от медленной загрузки.

`MAX_BODY_BYTES`, `SHUTDOWN_TIMEOUT` и сетевые сроки (`ReadTimeout`,
`SetReadDeadline`) — три независимых ограничения с разным смыслом:
объём тела, бюджет осушения при остановке, срок чтения на уровне
транспорта. Сетевые сроки чтения в этот каркас не добавлялись —
защиты от медленного читающего клиента на transports-уровне здесь
нет, и это зафиксировано как ограничение, а не скрыто.

Windows-оговорка: graceful-остановку сигналом из скрипта на Windows
не проверяли (taskkill/Stop-Process используют только для принудительной
уборки процесса после опыта, это не имитация Ctrl+C); путь
`SetReady(false) → Shutdown → DeadlineExceeded → выход процесса`
подтверждён интеграционным тестом в процессе. Kubernetes и контейнер
Linux этим опытом не проверялись.
