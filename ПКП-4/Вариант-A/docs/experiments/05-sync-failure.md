# Эксперимент: сбои синхронной проверки лимитов

## Условия

Проверялся HTTP-адаптер `internal/limits/httpclient`. Контракт вызова:

```http
POST /v1/limits/check
Idempotency-Key: limit:<operation-id>
Content-Type: application/json

{"subject":"ivan","limit":"active-applications-per-author"}
```

Положительный ответ: `200 OK` и `{"allowed":true}`. Бизнес-отказ передаётся тем же статусом с `allowed:false`; повторять такой запрос нельзя. К временным ошибкам отнесены транспортная ошибка, `429` и ответы `5xx`.

В тестах задержка retry и jitter заменены детерминированными функциями. Тесты проверяют число попыток и переданные значения, не завися от часов и случайных чисел.

## Результаты

| Сценарий | Наблюдение |
|---|---|
| Два ответа `503`, затем успех | Выполнено ровно 3 HTTP-вызова. Во всех запросах передан один ключ `limit:submit:a-1`. |
| Отмена контекста во время HTTP-вызова | Адаптер завершился с `context.Canceled`; следующая retry-попытка не запускалась. |
| 21 одновременный вызов при bulkhead `20` | 20 запросов вошли в HTTP-обработчик, 21-й сразу получил `limits.ErrBusy`. Зафиксированный максимум равен 20. |
| `allowed:false` | Возвращён `limits.ErrDenied`, HTTP-вызов выполнен один раз. |

## Связь с заявкой

`Application.Submit` проверяет лимит `active-applications-per-author` до изменения агрегата. Субъектом служит автор заявки. Идентификатор `submit:<application-id>` даёт один `Idempotency-Key` для всех попыток логического вызова. При отказе заявка остаётся в состоянии `DRAFT`.
